# ADR-0001: Record significant decisions as ADRs

## Status

Accepted

**Date:** 2026-11-14
**Deciders:** Tristan Rivoallan

## Context

I maintain several repositories alone, and come back to most of them after
weeks or months away. The code shows what was built, never why: why this
library and not the obvious one, why a constraint that looks arbitrary is
there, which option was already tried and dropped. That reasoning lives in my
head, in a chat transcript or in a commit message nobody will find again.

Two forces make this worse over time:

- **Coding agents.** Agents now write and change a large share of the code.
  Without the reasoning written down, an agent "fixes" a deliberate choice or
  reopens a question already settled, and I pay for the same debate twice.
- **The same questions across repositories.** Many decisions (tooling,
  layout, release practice) are not specific to one repository. Re-deciding
  them per repository drifts; copy-pasting the reasoning goes stale.

## Decision

We will record every significant decision in each repository as an
Architecture Decision Record, in Michael Nygard's lightweight format
(Status, Context, Decision, Consequences, plus Alternatives Considered and
References).

- **Significant** means: it constrains future work, it was chosen among real
  alternatives, or someone (human or agent) would reasonably question it
  later. Routine implementation choices are out of scope.
- **Where:** `docs/adr/` in the repository. ADRs inherited from a shared
  source live in `docs/adr/<alias>/`, imported with
  [ontrack](https://github.com/trivoallan/ontrack).
- **Decisions shared across repositories** are written once, in this
  repository, and shipped as an ontrack source. A repository-specific ADR
  stays in that repository.
- **Lifecycle:** an ADR starts `proposed`, becomes `accepted`, and later
  `deprecated` or `superseded` by a newer ADR. An accepted decision is not
  rewritten to say something else: a new ADR supersedes it.
- **Revision:** every ADR carries a `revision:` in its frontmatter. It is
  bumped only when the question itself moves (new context, changed
  decision), not for typo or wording fixes, so `ontrack plan` reports a
  `revised` ADR only when consuming repositories have something to look at.

## Consequences

### Positive

- The "why" survives my absence and reaches agents: they can read the ADRs
  before touching a deliberate choice.
- A settled question has an address. "See ADR-0003" ends a debate instead of
  restarting it.
- Shared decisions are written once and propagate through `ontrack plan`;
  drift between repositories becomes visible as a `revised` or `new` line.
- Writing the Consequences section forces the trade-offs into the open
  before the decision ships, not after.

### Negative

- Writing an ADR costs time, which is exactly when I least want to spend it.
  The risk is that ADRs get skipped for the decisions that most need them.
- ADRs can go stale silently: a superseded practice with no superseding ADR
  keeps looking authoritative.
- The `revision:` rule relies on judgment. Bump too often and consumers learn
  to ignore `revised`; too rarely and real changes slip through.

### Neutral

- Consuming repositories take a dev dependency on ontrack and on this
  repository; that is the price of sharing, not a side effect.
- ADRs are public here. Anything that should not be public stays out of the
  shared source and goes in a repository-specific ADR.

## Alternatives Considered

### Commit messages and PR descriptions only

Free, and already written. But they describe a change, not a standing
decision, and they are found by archaeology, not by browsing. An agent will
not dig through `git log` before editing a file.

### A single DECISIONS.md or wiki page per repository

Lower ceremony. But one file has no per-decision status, no stable
identifier to cite, and no unit ontrack can version and compare. A wiki also
leaves the repository, so agents working in the checkout never see it.

### A heavier format (MADR with decision drivers, or arc42 section 9)

More structure for weighing options. For a single maintainer the extra
sections become boilerplate and raise the cost of writing an ADR, which is
the main way this practice fails. Nygard's format keeps the floor low;
Alternatives Considered covers what matters from the heavier formats.
