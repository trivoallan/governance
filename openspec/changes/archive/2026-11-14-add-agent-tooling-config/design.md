# Design

## Context

- The main checkout's `.claude/` holds `skills/` (12 `openspec-*`
  skills), `commands/opsx/` (12 commands), `settings.local.json`
  (personal permissions) and `worktrees/`. All untracked; this worktree's
  `.claude/` holds only `settings.local.json`.
- Every skill and command carries `generatedBy: "1.13.1"` and
  `allowed-tools: Bash(openspec:*)`. The installed CLI is 1.13.1.
- `.claude/worktrees/` is ignored by `.git/info/exclude`,
  `settings.local.json` by the maintainer's `~/.config/git/ignore`; the
  repository's `.gitignore` covers neither.
- `governance-check ADR-0017` checks only that `.claude/settings.json` is
  tracked. ADR-0017 fixes the rest (rules 1 to 5).

## Goals / Non-Goals

**Goals:** ADR-0017's two files in place and its check passing; the
OpenSpec skills reviewed, committed and reproducible; local agent state
ignored by the repository itself.

**Non-Goals:** choosing plugins on the maintainer's behalf; moving
personal permissions into the shared settings; a check of the
marketplace's SHAs.

## Decisions

**Marketplace name `ontrack-trivoallan-tools`** (maintainer's choice). The
convention is `ontrack-<source namespace>-tools`, the namespace being
`package.json`'s `ontrack.namespace` (`trivoallan`). It is not an upstream
name (`melodic-software`, `superpowers-marketplace`,
`claude-plugins-official`…) nor a reserved one, and says whose it is.

**The plugin list is admitted entry by entry.** Each entry runs code in
every session, so the agent proposes and the maintainer approves each one
with its source and reviewed commit, in the ADR-0020 declaration form. The
candidates are the `Suggested skills` of the ADRs this repository works
under most: `claude-security` (ADR-0015), `plugin-dev` (ADR-0017),
`superpowers` (ADR-0009, ADR-0007), `source-control` (ADR-0006, ADR-0009).
The maintainer picked `superpowers`, `claude-security` and
`source-control`; `plugin-dev` is left out. Each still gets its source and
reviewed commit declared before its entry is written.
A SHA is resolved with `gh api repos/<owner>/<repo>/commits/<tag>` at a
tagged release when there is one. If the maintainer approves none yet, the
marketplace ships with an empty `plugins` list, provided Claude Code
accepts it; otherwise it waits for the first approved entry.

**`claude-security` is enabled from `claude-plugins-official`, unpinned**
(maintainer's choice). `claude plugin validate` refuses a plugin name
starting with `claude-` in a marketplace that is not Anthropic's, so the
entry cannot live in `ontrack-trivoallan-tools`. `.claude/settings.json`
enables `claude-security@claude-plugins-official` directly; the official
marketplace is known to Claude Code without an `extraKnownMarketplaces`
entry. ADR-0017 records it as a departure from rule 4. *Alternatives:*
renaming the entry (its `plugin.json` keeps the reserved name, untested);
leaving the plugin out. Rejected by the maintainer.

**A SHA is at least three days old.** As ADR-0018/ADR-0020's cooldown asks:
`superpowers` at tag `v7.0.2`; `source-control`, whose repository has no
tags, at the last `main` commit dated on or before three days back that
still holds `plugins/source-control`.

**OpenSpec skills: the pinned CLI is the tag, a regeneration is the hash
check.** ADR-0017 rule 3 asks for a fetch at a tag and a hash. These files
are not fetched but generated by `openspec init`/`update`; the equivalent
is to regenerate them with OpenSpec 1.13.1 and require an empty diff, which
checks every byte rather than a stored digest that could drift from the
files. The pull request lists the CLI version and the `shasum -a 256` of
each file for the reviewer. *Alternative:* a committed checksum manifest.
Rejected: one more file to keep in step, checking nothing the regeneration
does not.

**`allowed-tools: Bash(openspec:*)` is accepted.** It pre-approves only the
OpenSpec CLI, which writes under `openspec/`; the review states it in the
pull request. Bumping OpenSpec later regenerates the files in a reviewed
pull request, like a SHA bump.

**`settings.json` holds only the marketplace and plugins.** Permissions in
`settings.local.json` are one person's, and a shared allow-list is a
separate decision.

**The main checkout is cleaned before it pulls.** Its untracked copies of
`.claude/skills/` and `.claude/commands/` would block `git pull`. Once the
committed copies are confirmed identical (the regeneration above), the
untracked ones are removed there and the pull brings them back tracked.

## Risks / Trade-offs

- [Pinned SHAs go stale] → Bumping is a reviewed pull request, as ADR-0017
  accepts.
- [`claude-security` follows the official marketplace's head] → Accepted
  in ADR-0017's departure: that marketplace is Anthropic's.
- [A contributor already has a plugin from its upstream marketplace] → They
  turn that copy off in `settings.local.json`, as ADR-0017 says; the README
  repeats it.
- [The marketplace and vendored skills do not load in cloud sessions] →
  Accepted by ADR-0017.
