# Design

## Context

`main` holds ADR-0001 to ADR-0019 (ADR-0019 "Vulnerabilities"); ADR-0020
"Adding a dependency" is in open PR trivoallan/governance#17
(`adr/ADR-0020-adding-dependencies.md`, traits `admission.approver` and
`admission.install_scripts`) and must land first. ADR-0012's
`delivery.target` says whether a repository publishes (`package`,
`container`) or not (`platform`, `none`). See proposal.md for why.

Facts this design relies on, read on 2026-11-14 (task 1.1 re-checks each):

- **SLSA v1.x Build track** has levels 0 to 3. L0: no guarantee. L1:
  provenance exists, showing how the package was built. L2: the provenance
  is signed and generated by a hosted build platform, which defends against
  tampering after the build. L3: the hosted platform is hardened, isolating
  runs from one another and keeping signing material out of reach of the
  build steps, which defends against tampering during the build. v1.1
  keeps the same Build levels as v1.0; v1.2 reorganises the pages without
  changing them.
- **GitHub artifact attestations** (`actions/attest-build-provenance`,
  a wrapper over `actions/attest` since v4) sign an in-toto SLSA provenance
  with a short-lived Sigstore certificate tied to the workflow's OIDC
  identity and store it in GitHub's attestations API. They need
  `id-token: write` and `attestations: write`. GitHub states they reach
  **Build L2** alone, and L3 when the build runs in a reusable workflow
  that isolates it from the caller.
- **Verification**: `gh attestation verify <artifact> -R <owner/repo>`
  (or `oci://` for images); `npm audit signatures` checks registry
  signatures and npm provenance attestations of installed packages.
- **Plan limits**: npm provenance needs a public `repository` matching the
  source it is published from; GitHub artifact attestations on private or
  internal repositories need GitHub Enterprise Cloud, and are public-only
  on Free, Pro and Team (actions/attest-build-provenance README). PyPI's
  pages do not say whether Trusted Publishing works from a private
  repository, so the ADR says nothing about it.
- **Python verification**: no installer verifies PEP 740 attestations;
  `pypi-attestations verify pypi` is a separate step (ADR-0020).
- **npm provenance**: `npm publish --provenance` from a supported CI
  (GitHub Actions with `id-token: write`) publishes a Sigstore-signed SLSA
  provenance linked to the commit and workflow; trusted publishing (OIDC,
  no long-lived token) produces it automatically.
- **PyPI**: Trusted Publishing (OIDC) with `pypa/gh-action-pypi-publish`
  uploads PEP 740 attestations by default.
- **slsa-github-generator** provides reusable workflows that build or sign
  in a job isolated from the caller, the classic L3 path on GitHub.

## Goals / Non-Goals

**Goals:**
- An agent setting up a release knows whether to attach a provenance and
  which mechanism to use.
- Tie the key to ADR-0012 so a repository that publishes nothing is not
  asked.

**Non-Goals:**
- Verifying dependencies' provenance: ADR-0020's admission rule.
- SBOMs, signing of commits or tags, reproducible builds.
- SLSA's Source track (v1.2): branch protection is ADR-0009 and ADR-0011.
- Publishing governance to npm: a separate change; this one only cites it.

## Decisions

### One enum key holding the SLSA level

The level is the question; the mechanism follows from the registry. Keys
per mechanism (`attest`, `npm-provenance`) would date with the tools.
Alternative: a boolean `provenance`. Not chosen: it cannot tell L1 (an
unsigned file) from L2, the distinction that matters. The schema enum holds
the integers `0`…`3`: mdschema compares typed values, and an integer enum
accepts the natural `build_level: 2` while refusing `"2"` and `4` (checked
in task 1.2).

### L2 recommended, L3 as an alternative

On GitHub-hosted runners L2 is a few lines and no key. L3 asks for the
build to move into a reusable workflow or `slsa-github-generator`, which
restructures the release workflow, couples it to that generator's release
cadence, and buys protection against a compromised step inside the build,
a threat most small repositories do not model. Stated under Alternatives
with that cost.

### Applicability follows what leaves the repository

`delivery.target` (`package` or `container`), not `release_tool`. ADR-0012
rules that a repository publishing a package answers `manual`, never
`none`; conditioning on `release_tool` would exempt the hand release, the
workstation-token case this ADR targets and rule 3 forbids. A repository
with `platform` or `none` rules ADR-0021 `rejected`, the full answer
ADR-0001 already defines.

### Verification is pointed to, not ruled

Who verifies is the consumer; governance's consumer-side rule lives in
ADR-0020. ADR-0021 names the commands and links there instead of adding a
second key.

## Risks / Trade-offs

- [ADR-0020 not merged] → ADR-0021's link and the table's count break if it
  lands first. Mitigation: task 3.1 rebases on ADR-0020 and checks the link.
- [Enum of digits read as integers] → task 1.2 tests a ruled sample.
- [GitHub's L2/L3 claim changes] → the References carry the read date.
